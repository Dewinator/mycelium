## Question this spike answers

Sub-task 8 of #176 says: *"build all three installers per release tag, sign + notarize macOS, sign Windows."* Five load-bearing decisions need a written-down recommendation before the workflow lands:

1. **Trigger model** — release-tag, manual dispatch, or both?
2. **Build matrix** — which OS / arch combos for MVP, which deferred?
3. **Signing & notarization** — toolchain per platform + secret custody?
4. **Update manifest** — who generates `latest.json`, where does it live, how is it signed?
5. **Beta/stable channel separation** — one feed or two?

## TL;DR

- **Tag-triggered, with manual-dispatch fallback.** `git tag v0.x.y && git push --tags` is the canonical release. `workflow_dispatch` exists for emergency rebuilds without a new tag (e.g. cert rotation).
- **Four artifacts on day-one:** macOS arm64 (Apple Silicon), macOS x86_64 (Intel), Windows x86_64, Linux x86_64 AppImage. **No Linux .deb/.rpm in MVP** — AppImage is universal and matches Tauri's default output.
- **Signing toolchains:** macOS Apple Developer ID + `notarytool` (paid cert, Reed's account); Windows **Azure Trusted Signing** (cheaper than buying a 3-year EV cert directly, ~$10/mo, no HSM); Linux AppImage **unsigned** (the Tauri-updater signature on the payload itself is sufficient — Pillar 6 holds).
- **`latest.json` generated by tauri-action, committed to the GitHub Release.** Signed with the same `tauri signer` key from the Tauri spike. Fetched by clients at `https://github.com/Dewinator/mycelium/releases/latest/download/latest.json` — no separate update server.
- **Two channels via two manifests.** `latest.json` (stable) and `latest-beta.json` (pre-release tags `v*-beta.*`). `tauri.conf.json` reads channel from a runtime env var so power-users can flip to beta without reinstalling.

## Recommended workflow

`.github/workflows/release.yml` (sketch — actual file lands in the implementation ticket):

```yaml
name: release
on:
  push:
    tags: ['v*']
  workflow_dispatch:
    inputs:
      tag: { description: 'Tag to rebuild', required: true }

jobs:
  build:
    strategy:
      fail-fast: false
      matrix:
        include:
          - { os: macos-14,        target: aarch64-apple-darwin,    label: macos-arm64 }
          - { os: macos-13,        target: x86_64-apple-darwin,     label: macos-x64   }
          - { os: windows-latest,  target: x86_64-pc-windows-msvc,  label: windows-x64 }
          - { os: ubuntu-22.04,    target: x86_64-unknown-linux-gnu,label: linux-x64   }
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22', cache: 'npm', cache-dependency-path: mcp-server/package-lock.json }
      - uses: dtolnay/rust-toolchain@stable
        with: { targets: ${{ matrix.target }} }

      - name: Install Linux deps
        if: runner.os == 'Linux'
        run: sudo apt-get update && sudo apt-get install -y libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev

      - name: Build mcp-server sidecar
        working-directory: mcp-server
        run: npm ci && npm run build && npm run bundle:sidecar  # produces dist/sidecar/mycelium-mcp-${{ matrix.target }}

      - uses: tauri-apps/tauri-action@v0
        env:
          # macOS
          APPLE_CERTIFICATE: ${{ secrets.APPLE_CERTIFICATE }}              # base64 .p12
          APPLE_CERTIFICATE_PASSWORD: ${{ secrets.APPLE_CERTIFICATE_PASSWORD }}
          APPLE_SIGNING_IDENTITY: ${{ secrets.APPLE_SIGNING_IDENTITY }}    # "Developer ID Application: …"
          APPLE_ID: ${{ secrets.APPLE_ID }}
          APPLE_TEAM_ID: ${{ secrets.APPLE_TEAM_ID }}
          APPLE_PASSWORD: ${{ secrets.APPLE_PASSWORD }}                    # app-specific password
          # Windows (Azure Trusted Signing)
          AZURE_TENANT_ID: ${{ secrets.AZURE_TENANT_ID }}
          AZURE_CLIENT_ID: ${{ secrets.AZURE_CLIENT_ID }}
          AZURE_CLIENT_SECRET: ${{ secrets.AZURE_CLIENT_SECRET }}
          # Tauri updater signing (cross-platform)
          TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
          TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ${{ secrets.TAURI_SIGNING_KEY_PASSWORD }}
        with:
          tagName: ${{ github.ref_name }}
          releaseName: 'mycelium ${{ github.ref_name }}'
          releaseDraft: true
          prerelease: ${{ contains(github.ref_name, '-beta') }}
          args: --target ${{ matrix.target }}

  publish-manifest:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Generate latest.json from release artifacts
        env: { GH_TOKEN: ${{ secrets.GITHUB_TOKEN }} }
        run: scripts/generate-latest-json.ts ${{ github.ref_name }}
      - name: Attach to release
        run: gh release upload ${{ github.ref_name }} latest.json --clobber
```

## The five decisions, with sources

### 1. Trigger: tag push, with manual fallback

`on: push: tags: ['v*']` is the GitHub-native idiom. Pre-release tags follow the SemVer convention `v0.2.0-beta.1` — `contains(github.ref_name, '-beta')` flips Tauri's `prerelease` flag and routes the `latest.json` to the beta manifest in step 5.

`workflow_dispatch` with a `tag` input lets us rebuild without retagging when a cert expires or a CI runner image changes mid-cycle. We do NOT trigger on every push to main — that would burn the macOS minutes budget and produce unsigned dev builds the updater would reject anyway.

### 2. Build matrix: 4 artifacts, AppImage-only Linux

The four targets cover the 95th percentile of the FB-group audience the epic identifies:

| Target | Runner | Rust target | Output |
|---|---|---|---|
| macOS arm64 | `macos-14` | `aarch64-apple-darwin` | `mycelium_0.x.y_aarch64.dmg` + `.app.tar.gz` |
| macOS x64 | `macos-13` | `x86_64-apple-darwin` | `mycelium_0.x.y_x64.dmg` + `.app.tar.gz` |
| Windows x64 | `windows-latest` | `x86_64-pc-windows-msvc` | `mycelium_0.x.y_x64-setup.nsis.zip` (NSIS, not MSI — Tauri default; lighter, signs cleanly with Trusted Signing) |
| Linux x64 | `ubuntu-22.04` | `x86_64-unknown-linux-gnu` | `mycelium_0.x.y_amd64.AppImage.tar.gz` |

**Out of MVP:** Linux arm64, Windows arm64, .deb/.rpm, Snap, Flatpak. Each adds a runner + a signing/distribution variant. Path: ship MVP, see what shows up in the issue tracker, add the next-most-asked target after launch.

`fail-fast: false` is critical — a one-off cert glitch on Windows shouldn't kill macOS artifacts that are already signed and notarized.

### 3. Signing & notarization

**macOS:** Apple Developer ID Application certificate, exported as `.p12`, base64-encoded into `APPLE_CERTIFICATE`. Tauri's bundler runs `codesign` with hardened-runtime + entitlements, then `notarytool submit --wait` (replacing the deprecated `altool` flow). [Apple deprecated `altool` in Nov 2023](https://developer.apple.com/documentation/security/notarizing_macos_software_before_distribution); `tauri-action` uses `notarytool` natively when given the env vars above.

**Windows:** **Azure Trusted Signing**, not a standalone EV cert. Reasoning:
- Standalone EV cert: $300–500/yr, requires a hardware HSM/YubiKey, painful to plug into a CI runner.
- Trusted Signing: ~$10/month flat, OAuth-token-based, designed for CI. Same SmartScreen reputation outcome.
- Tauri 2 supports it natively via `windows.signCommand` config + `azuresigntool` (community wrapper, audited). [Microsoft Trusted Signing GA'd Oct 2024.](https://learn.microsoft.com/en-us/azure/trusted-signing/)

**Linux:** AppImage is **not OS-signed** in MVP. The integrity guarantee for a Linux user is the **Tauri-updater Ed25519 signature on the `.AppImage.tar.gz` payload**, verified by the running app before the update is applied. This is the exact same guarantee macOS and Windows users get *in addition to* OS-level codesigning — Linux just has no OS-level layer to add. Pillar 6 explicit verdict: acceptable, since the threat model is "tampered update download", which the payload signature covers.

**Secret custody:** all secrets in GitHub Actions repo-secrets, rotated on a 12-month cadence (calendar reminder in `docs/release-runbook.md` once that ticket lands). The Tauri-updater **private key** lives ONLY in the secret store + Reed's local 1Password — never in CI logs, never in the repo, never on a dev laptop's disk in plaintext. Same hygiene as PRs #188 / #189's GGUF SHA-256 verification.

### 4. `latest.json` generation

`scripts/generate-latest-json.ts` (new, ~50 lines) runs on the `publish-manifest` job AFTER all four builds succeed. It:

1. Calls `gh release view ${tag} --json assets` to enumerate the four artifact URLs.
2. Reads each `.sig` file (Tauri's bundler emits one per platform alongside the artifact).
3. Emits `latest.json` matching the schema in the [Tauri-shell spike § decision 5](native-tauri-shell-spike.md):

```json
{
  "version": "0.2.0",
  "notes": "<release notes from tag annotation>",
  "pub_date": "<ISO 8601>",
  "platforms": {
    "darwin-aarch64": { "signature": "...", "url": "https://github.com/Dewinator/mycelium/releases/download/v0.2.0/mycelium_0.2.0_aarch64.app.tar.gz" },
    "darwin-x86_64":  { "signature": "...", "url": "..." },
    "windows-x86_64": { "signature": "...", "url": "..." },
    "linux-x86_64":   { "signature": "...", "url": "..." }
  }
}
```

4. Uploads `latest.json` to the release via `gh release upload --clobber`. The Tauri client polls `https://github.com/Dewinator/mycelium/releases/latest/download/latest.json` — GitHub's redirect always points the `/latest/` URL at the most recent non-prerelease release.

We do NOT host this on a custom server. Everything stays on GitHub Releases until volume forces a CDN move (a problem worth having, not solving today).

### 5. Beta channel: separate manifest, same workflow

Pre-release tags (`v*-beta.*`) skip the `/latest/` redirect because GitHub treats them as prereleases. The `publish-manifest` job branches on `prerelease`:

- Stable tag → uploads `latest.json` to the stable release. Auto-installed by stable-channel users.
- Beta tag → uploads `latest-beta.json` to the prerelease. Only installed by users who flipped `MYCELIUM_UPDATE_CHANNEL=beta` in Settings.

Tauri reads the channel at boot; the updater plugin's `endpoints` config can be a runtime function that picks the URL. One workflow, two outcomes, no duplicated code. This costs ~10 lines in the Tauri shell and keeps the dogfood loop tight (Reed runs beta on his daily-driver Mac, stable goes to FB-group users).

## What this spike does NOT answer

Honest list of unknowns deferred to implementation:

- **macOS x86_64 dropping date.** Apple's own dev-tools dropped Intel Macs from the build matrix in late 2024. Recommend keeping the x64 macOS runner for ~12 months post-MVP, then re-evaluate.
- **Sidecar binary bundling step.** `npm run bundle:sidecar` is hand-waved above. Whether it's `pkg`, `bun build --compile`, or `node --experimental-sea-config` depends on which one survives node-llama-cpp's native module resolution — needs an empirical mini-spike when the implementation ticket starts.
- **CI minutes budget.** macOS minutes are 10× Linux. Four-target matrix with 30-min builds = ~3 hr macOS minutes per release × 1-2 releases/week = comfortably inside the GitHub free tier for a public repo, but worth measuring after the first three releases.
- **Notarization wait time.** `notarytool submit --wait` historically takes 5-15 minutes. CI timeout per job set to 60 min to absorb worst-case Apple backlog.
- **Windows runner cost of Azure Trusted Signing.** ~$10/mo flat fee on Reed's Azure tenant, paid out-of-band like Apple Developer ID. Documented in the runbook, not in code.
